# ソフトウェア設計

想定する仕様変更を一つ当てはめ、案の採否が変わる観点で比べる。

## 責任と変更範囲

- 種類を一つ増やすたびに複数の呼び出し側が分岐を変えるなら、振り分けを集約し、呼び出し側には必要な結果だけを返す。
- 抽象化は変えたい軸に限る。経路を差し替えるために、各工程の内部まで揃えない。
  - 名前や引数が似ていても、独立に変わる仕様は共通化しない。
- 任意機能のために隣のシステムの内部事情を追跡するなら、結合を受け入れる案と、要件を緩めて境界を保つ案を比べる。

## 状態の更新

- 状態ごとに、正本の持ち主と値が確定する契機を決める。
  - 別経路で同じ値を取り直すなら、何が古くなり、どちらを採用するのかを明らかにする。
- 再送・再計算・キャッシュ無効化を最適化する前に、そのタイミングで値が変わりうるかを確かめる。

## データの契約

- フィールドは取得元や保存型でなく、何を表すかで定義する。同じ日時型でも、出来事の時刻と保存時刻は別の概念である。
- API の返却値は内部レコードから不要項目を引くのでなく、公開する項目を明示して組み立てる。

## いつ決めるか

後から取り戻せない観測は収集時に決め、保存したデータから選び直せる集計法までは固定しない。

## 失敗の影響範囲

失敗した工程と理由を識別できる形で返し、まだ有効な途中結果や接続は保つ。
